\abstract{%
Multi-instance vLLM deployments commonly place an L7 balancer such as
Round-Robin or least-connections in front of independent inference replicas.
Those balancers treat peers as equal capacity units, yet queues, KV-cache pressure,
and temporary slowdowns still diverge across replicas. We present \textbf{DIO}
(\texttt{dio-serve}), a thin OpenAI-compatible gateway that ranks backends from
black-box end-to-end telemetry using dual-timescale NLMS, without engine
modifications and without requiring an offline latency/throughput
performance-capacity model before deployment. Optional Prometheus scrape,
session affinity, and admission modes are supported as operational extensions.

On matched dual Tesla~T4 replicas, DIO remains near Round-Robin parity. Under a
controlled $\times2$ service-time gap, mean p99 improves by $48.3\%$ (SD~$0.7\%$)
over Round-Robin ($n{=}10$). On a physically heterogeneous T4$+$A30 pair with
identical model weights and no injected delay, DIO routes $89.5\%$ of mixed-length
traffic to the lower-latency A30 and improves mean p99 by $33.3\%$ (SD~$17.4\%$)
relative to Round-Robin across five paired seeds, winning on p99 in all five; an
offset five-seed robustness cell reproduces the A30-directed routing. Offline
regression confirms the learned ordering. Finally, the same online model is useful
for ranking but too poorly calibrated for a direct absolute latency gate, which
rejects $\sim$40\% of otherwise completed dual-T4 requests. Source code and
experimental artifacts are publicly available.

\medskip
\noindent\textbf{Keywords:} LLM serving, heterogeneous GPU clusters, online
routing, load balancing, vLLM, latency ranking, NLMS.
}

\section{Introduction}
\label{sec:intro}

Multi-instance vLLM~\cite{vllm} (or SGLang/TGI~\cite{sglang,tgi,radixattention})
deployments commonly place an L7 gateway such as Nginx~\cite{nginx}, Kubernetes
Services~\cite{kubernetes}, Envoy~\cite{envoy}, or Ray Serve~\cite{rayserve} in
front of independent inference replicas with Round-Robin or least-connections.
Single-node engines optimize continuous batching~\cite{orca,bullet}; they do not
solve \emph{which backend} should take the next request. Classic L7
balancers~\cite{maglev,nginx} treat backends as equal capacity units.

In production, effective cost still diverges even on identical GPU types: pending
queues grow unevenly, KV-cache utilization spikes on one replica, prefix caches
favor sessions pinned to a peer, and host interference can temporarily slow one
process. The result is avoidable tail latency~\cite{dean2013tail}. Co-designed
cluster schedulers~\cite{nexussched,llumnix,loongserve} can react with deep engine
hooks or live KV migration, but many operators need a non-invasive front door that
wraps unmodified OpenAI-compatible~\cite{openaiapi} inference APIs without patches.

A second problem arises when the same online latency model is used for admission
control. Models learned from black-box end-to-end telemetry are often accurate only
as \emph{relative rankers}. On dual Tesla~T4 we measure dual-timescale
NLMS~\cite{haykin2002adaptive} MAPE of $\sim$90--130\%. Gating admission on
``reject if $\min\hat{y}>\mathrm{SLO}$'' inherits that error and can starve healthy
traffic.

We design \textbf{DIO} (\texttt{dio-serve}) as a thin control plane for this
multi-instance pattern (Figure~\ref{fig:architecture}). Its core loop uses request
telemetry (e2e latency, tokens, and gateway pending) to rank backends online. When
available, DIO can additionally consume engine metrics from each vLLM Prometheus
endpoint~\cite{prometheus}. The gateway is HTTP-only and leaves the engine source
and runtime unmodified. Optional session affinity and admission modes are reported
as operational capabilities rather than as the central performance claim.

Empirically, DIO remains near Round-Robin parity on homogeneous dual-T4 peers,
responds to a controlled service-time gap, and routes mixed-length traffic to the
lower-latency GPU in a T4$+$A30 pair without requiring an offline
latency/throughput performance-capacity model before deployment
(Section~\ref{sec:regimeD}). We separately report the admission failure mode caused
by treating a relative ranker as an absolute SLO predictor.

\paragraph{Contributions}
\begin{enumerate}
\item \textbf{Online routing from black-box telemetry.} DIO uses dual-timescale
NLMS ($O(1)$ updates) to rank unmodified vLLM workers from end-to-end latency and
token counts under an OpenAI-compatible HTTP boundary, without requiring an offline
latency/throughput model before deployment.
\item \textbf{Evaluation on physically heterogeneous GPUs.} On real T4$+$A30
unmodified vLLM (no injected delay), dual-timescale NLMS matches $d{=}2$ RLS on
central p99 while routing more cleanly to the A30 ($89.5\%$ mean frac) and
improving mean p99 by $33.3\%$ (SD~$17.4\%$) over Round-Robin in five paired seeds.
An offline OLS fit is a post-hoc ordering check, not a control input.
\item \textbf{Admission calibration analysis.} Homogeneous parity and a controlled
slow-peer experiment frame the ranking claim; we show that a ranker with high
absolute error must not be used directly as an SLO threshold.
\end{enumerate}
\noindent Implementation, scripts, and multi-seed artifacts for the dual-T4 and
T4$+$A30 experiments are released with the paper (Declarations).

\section{Background and related work}
\label{sec:related}

\subsection{Single-node engines and prefix/KV systems}
vLLM~\cite{vllm} popularized PagedAttention and continuous batching; alternatives
revisit memory management without paging~\cite{vattention}.
SGLang~\cite{sglang,radixattention} improves structured decoding and RadixAttention
prefix reuse. TGI~\cite{tgi} targets production APIs. Hybrid iteration policies
include Sarathi-Serve~\cite{bullet} and FastServe~\cite{fastserve}. Disaggregated
prefill/decode systems~\cite{distserve,splitwise,mooncake,memserve} optimize pipeline
stages and KV placement. Prefix/KV reuse~\cite{promptcache,hydragen,cacheblend,lmcache,preble}
raises the value of \emph{where} a request lands. These systems excel on one node or a
co-designed cluster; multi-worker routing in front of \emph{unmodified} engines remains
external.

\subsection{Cluster orchestrators and classical serving}
Ray Serve~\cite{rayserve} and Triton~\cite{triton} emphasize actors and model
repositories with coarse metrics. Earlier DNN serving stacks
(Clipper~\cite{clipper}, INFaaS~\cite{infaas}, Clockwork~\cite{clockwork})
established predictability and model-selection themes that LLM gateways inherit.
Orca~\cite{orca} advances iteration-level batching. AlpaServe~\cite{alpaserve} and
CoCoServe~\cite{CocoServe} focus on placement and multiplexing. M\'{e}lange~\cite{melange}
targets heterogeneous capacity tables. NexusSched~\cite{nexussched} combines
predictive routing with engine co-design and multi-feature predictors ($O(d^2)$
updates). Llumnix~\cite{llumnix} migrates live KV state. LoongServe~\cite{loongserve}
targets long-context elastic parallelism. ServerlessLLM~\cite{serverlessllm}
optimizes cold-start loading.

\textbf{Inference-aware gateways.}
Metrics-, prefix-, and KV-aware routing over unmodified vLLM is already deployed
infrastructure. The Kubernetes Gateway API Inference
Extension~\cite{gaie} and its Endpoint Picker select replicas using scraped vLLM
queue depth, KV utilization, and LoRA state; \mbox{llm-d}~\cite{llmd} and Google's
GKE Inference Gateway~\cite{gkeinference} build on it. NVIDIA
Dynamo~\cite{dynamo} scores endpoints by cached-prefix overlap. The vLLM
production-stack router~\cite{productionstack} ships round-robin, session,
prefix-aware, and KV-aware policies (including static backends without Kubernetes).
Alibaba's ACK/ACS gateway~\cite{alibabagw}, the SGLang router~\cite{sglangrouter},
and Envoy AI Gateway~\cite{envoyai} similarly offer cache- or LLM-aware balancing.
These systems establish that engine-metric and locality-aware routing are practical.

\textbf{Focus of this work.}
DIO is not intended to replace cluster-native or engine-co-designed schedulers.
Our contribution is narrower: we study whether a lightweight gateway can learn
relative per-replica service rates online from black-box end-to-end telemetry,
without engine modification and without requiring an offline latency/throughput
performance-capacity model before deployment, and we evaluate when such a model is
unsuitable for absolute admission. The routing signal is dual-timescale
NLMS~\cite{haykin2002adaptive} (Section~\ref{sec:nlms}) with $O(1)$ updates; closest
learned comparators either need engine co-design or $O(d^2)$
updates~\cite{nexussched}. On the physical cell, NLMS is not claimed to beat RLS on
mean p99; the systems argument is comparable ranking effectiveness with
constant-time updates and more stable routing (Section~\ref{sec:regimeD}). The same
online model that ranks well is badly miscalibrated in absolute terms (MAPE
$\sim$90--130\%, Section~\ref{sec:regimeA}), so a textbook absolute SLO gate rejects
$\sim$40\% of a load that empirical and rank-only gating complete in full
(Section~\ref{sec:evalC}). That negative calibration result is a caution for any
predictive admission controller built on black-box telemetry.
Section~\ref{sec:sys-compare} summarizes deployment trade-offs.

\subsection{Adaptive prediction, queues, and admission}
NLMS stability and step-size practice follow adaptive filter
theory~\cite{haykin2002adaptive,sayed2008adaptive}; recursive least squares is the
natural $O(d^2)$ comparator under the same linear feature model. A still simpler
baseline---ranking by per-worker exponentially weighted moving average (EWMA) of
recent e2e latency without a token feature---is a natural alternative that this
paper does not evaluate; establishing that dual-timescale NLMS is necessary rather
than merely sufficient relative to EWMA remains future work
(Section~\ref{sec:limitations}). Queue wait uses a batch-amortized Little-style
heuristic~\cite{littleslaw,kleinrock1975queueing}. SJF-style ranking motivates
predicted service routing~\cite{sjf}. Roofline~\cite{williams2009roofline} inspires
soft memory ceilings recast as routing penalties. Goodput- and SLO-aware LLM
serving~\cite{distserve,sloawarellm} motivates treating admission as a
separate policy from ranking. Simulation frameworks such as Vidur~\cite{vidur}
characterize offline capacity; DIO targets online multi-instance ranking under weak
absolute models.

\section{System design}
\label{sec:design}

\subsection{Architecture and software artifact}
\label{sec:architecture}
Figure~\ref{fig:architecture} shows \texttt{dio-serve}, the gateway used in all
experiments below. Clients issue OpenAI-compatible HTTP requests. A FastAPI control
plane ranks backends with dual-timescale NLMS, optionally folds in scraped engine
metrics, applies session affinity and admission, then proxies to an unmodified vLLM
worker. Completions update per-worker models from observed e2e latency and token
counts. A Go/gRPC research path exists in the repository but is not used for the
results in this paper.

\begin{figure}[H]
\centering
\includegraphics[width=0.58\columnwidth]{fig_architecture_dio.png}
\caption{DIO multi-instance gateway. Clients call \texttt{dio-serve}; the control
plane ranks unmodified vLLM replicas with NLMS, optional Prometheus scrape, session
affinity, and admission (no engine patches).}
\label{fig:architecture}
\end{figure}

Telemetry uses four signals: gateway e2e latency; token counts from response
\texttt{usage} or a tokenizer estimate; per-backend pending depth; and optional
HTTP scrape of each engine \texttt{/metrics}. Soft and hard VRAM limits come from
configuration or KV usage. Unlike NexusSched and Llumnix, which require engine hooks
or live migration~\cite{nexussched,llumnix}, DIO does not sample NVML
SM/power/temperature and does not modify engine source.

A typical launch is \texttt{dio serve -b e0=URL0 -b e1=URL1}. Background tasks
scrape \texttt{/metrics} every $1$\,s by default and probe health. Debug endpoints
report metrics, engine state, affinity, and admission counters. Scheduling overhead
is on the order of $10$--$15\,\mu$s per request in a local microbench
(Section~\ref{sec:overhead}). Source code, library multi-seed harnesses, and dual-T4
scripts are public (Declarations).

\subsection{Dual-timescale NLMS latency model}
\label{sec:nlms}
For worker $w$ and token count $N$ we use the linear model
\begin{equation}
\hat{y}_w = s_w N + b_w,
\label{eq:model}
\end{equation}
with slope $s_w$ (ms/token) and intercept $b_w$ (ms). After a completion with residual
$e = y - \hat{y}$, NLMS updates
\begin{equation}
s \leftarrow s + \mu \frac{e}{N}, \qquad
b \leftarrow b + \mu_b e,
\end{equation}
using dual rates $\mu_{\mathrm{fast}}{=}0.1$, $\mu_{\mathrm{slow}}{=}0.01$,
$\mu_b{=}0.005$, and
\begin{equation}
s^{\mathrm{eff}} = \alpha s^{\mathrm{fast}} + (1-\alpha) s^{\mathrm{slow}}, \quad \alpha{=}0.8.
\label{eq:dual}
\end{equation}
Priors are $s_0{=}2.0$\,ms/token and $b_0{=}150$\,ms. Arithmetic per update is
$O(1)$; slopes typically leave the prior after about $15$--$20$ completions per
worker. Figure~\ref{fig:nlms_conv} shows a simulated slope jump. The token feature
$N$ prefers Hugging Face tokenizer counts plus planned \texttt{max\_tokens}, with
fallback $\lfloor|\mathrm{prompt}|/4\rfloor+\texttt{max\_tokens}$.

\begin{figure}[ht]
\centering
\includegraphics[width=0.68\columnwidth]{fig_nlms_convergence_throttle.png}
\caption{Simulated dual-timescale NLMS under an injected slope jump at request 80.
$s^{\mathrm{fast}}$ adapts first; $s^{\mathrm{slow}}$ lags. Not dual-T4 wall-clock

\label{fig:nlms_conv}
\end{figure}

\subsection{Baseline joint cost}
\label{sec:cost-baseline}
Absent hybrid metrics, each healthy worker scores
\begin{equation}
S_w^{\mathrm{base}} =
\mathrm{wait}_w + \hat{t}_w + \mathrm{tierCost}_{r,w} + \mathrm{vramCost}_w
- \mathrm{cacheBonus}_w,
\label{eq:base}
\end{equation}
with $\hat{t}_w = s^{\mathrm{eff}}_w N + b_w$,
$\mathrm{wait}_w = (Q_w/B)\bar{t}_w$ ($B{=}8$), soft VRAM penalty when free VRAM
${<}4$\,GB, and hard exclusion when free VRAM ${<}2.4$\,GB and $N{>}1000$.
Operators may label each worker with an optional \emph{tier} index (an integer
capability class, e.g., small vs.\ large GPU or model size). Then
$\mathrm{tierCost}_{r,w}$ is a soft $500$\,ms penalty when the request's declared
size class exceeds the worker's tier, and a hard block applies when a large request
would land on a small-tier worker (``large-on-small''). In all dual-T4 and T4$+$A30
experiments in this paper, every worker shares the same tier, so
$\mathrm{tierCost}{=}0$ and hard tier blocks never fire; the term is retained for
mixed-capability fleets. Route to $\arg\min_w S_w$ in $O(|W|)$ time. Strategies also
include Round-Robin, Least-Loaded, static slopes, and $d{=}2$ RLS as head-to-head
baselines under the \emph{same} cost shell when applicable.

\section{Hybrid cost routing with engine metrics}
\label{sec:hybrid}

\subsection{Why engine metrics}
NLMS observes only gateway e2e latency and tokens. That signal is delayed, noisy,
and confounded by batching. Unmodified vLLM already exports internal state via
Prometheus~\cite{prometheus}: GPU KV-cache utilization, waiting/running request
counts, and prefix-cache hit counters. DIO optionally scrapes those gauges and
folds them into the same millisecond-scale cost used for ranking, without source
modification. The metric path is an operational extension; the primary ranking
evidence in this paper is NLMS from black-box e2e telemetry
(Sections~\ref{sec:regimeC}--\ref{sec:regimeD}).

\subsection{Metric scrape and snapshot}
For each backend $i$ with base URL $U_i$ and metrics path (default
\texttt{/metrics}), a background task issues \texttt{GET $U_i$/metrics} and parses
Prometheus exposition text. Metric name variants across vLLM versions are handled
(e.g.\ \texttt{vllm:gpu\_cache\_usage\_perc} vs.\ \texttt{vllm:kv\_cache\_usage\_perc};
prefix hit rate from a direct gauge or from hits/queries counters). Each scrape
yields a snapshot
\begin{equation}
\mathcal{E}_w = (\mathrm{KV}_w,\, W_w,\, R_w,\, \mathrm{Hit}_w,\, \mathrm{ok}_w),
\end{equation}
where $\mathrm{KV}_w\in[0,1]$, $W_w$ and $R_w$ are waiting/running request counts,
$\mathrm{Hit}_w\in[0,1]$ is prefix-cache hit rate, and $\mathrm{ok}_w$ is false on
HTTP/parse failure. On failure, hybrid terms contribute zero (graceful degrade to
NLMS-only ranking). Scrape interval defaults to $1$\,s---fast enough to track KV
pressure, slow enough not to contend with decode.

\subsection{Hybrid joint cost}
When $\mathrm{ok}_w$ is true, the full score is
\begin{equation}
\begin{aligned}
S_w ={}& \mathrm{wait}_w + \hat{t}_w + \mathrm{tierCost}_{r,w} + \mathrm{vramCost}_w \\
&+ c_{\mathrm{kv}}\,\mathrm{KV}_w + c_{q}\,W_w
- \mathrm{cacheBonus}_w - c_{p}\,\mathrm{Hit}_w.
\end{aligned}
\label{eq:hybrid}
\end{equation}
Default hybrid coefficients (same ms units as other terms): $c_{\mathrm{kv}}{=}800$,
$c_{q}{=}50$ per waiting request, $c_{p}{=}150$. These were chosen so that a
near-full KV cache ($\mathrm{KV}{\approx}1$) contributes on the order of one
long-request decode budget, a moderate waiting queue ($W{\approx}10$) is
comparable to a soft VRAM penalty, and a high engine prefix hit rate is of similar
scale to the session affinity bonus $C{=}200$\,ms---heuristic parity with existing
base cost terms. They are configuration defaults, not parameters optimized by the
physical-heterogeneity experiment; operators may override all three through
\texttt{DIO\_*} configuration.

If $\mathrm{KV}_w{>}0.95$ and $N{>}500$, worker $w$ is hard-blocked for that request
(engine-reported near-full KV). Free-VRAM estimates may be updated as
$\mathrm{free}_w \approx \mathrm{total}_w(1-\mathrm{KV}_w)$ when totals are known.
When backends differ only in learned service slope and metrics look similar, NLMS
ranking still dominates.

\begin{algorithm}[ht]
\caption{Worker selection with hybrid scrape, affinity, and admission}
\label{alg:dio}
\begin{algorithmic}[1]
\Require request $r$, workers $W$, mode $m$, optional snapshots $\{\mathcal{E}_w\}$
\State \emph{Background (async):} periodically scrape each backend \texttt{/metrics}
      into $\mathcal{E}_w$ (KV, $W$, Hit); on failure leave hybrid terms at 0
\State $N \leftarrow$ TokenFeature$(r)$; $w^\star\leftarrow\bot$; $S_{\min}\leftarrow\infty$
\ForAll{$w\in W$ healthy and tier-feasible}
  \State $\hat{t}_w \leftarrow$ Predict$(w,N)$
  \If{VRAM/KV hard-blocked$(w,N,\mathcal{E}_w)$} \textbf{continue}
  \EndIf
  \State $S_w \leftarrow$ wait$+\hat{t}_w+$tier$+$vram$+c_{\mathrm{kv}}\mathrm{KV}_w+c_q W_w$
  \Statex \hspace{\algorithmicindent}$-$cacheBonus$(r,w)-c_p\mathrm{Hit}_w$
  \If{$S_w < S_{\min}$} $S_{\min}\leftarrow S_w$; $w^\star\leftarrow w$
  \EndIf
\EndFor
\If{$w^\star=\bot$ \textbf{or} AdmissionReject$(S_{\min},m)$}
  \State \Return HTTP 503 with Retry-After
\EndIf
\State RecordPrefixAffinity$(r,w^\star)$; \Return $w^\star$
\end{algorithmic}
\end{algorithm}

\section{Session and prefix-cache affinity}
\label{sec:affinity}

\subsection{Why multi-turn affinity}
Round-Robin and least-connections scatter multi-turn sessions across replicas.
Each turn that lands on a cold replica re-prefills shared system prompts and agent
context, missing in-engine prefix caches~\cite{radixattention,promptcache,hydragen}.
Cache-aware and prompt-scheduling systems~\cite{preble,cacheblend} show large gains
when locality is preserved, but they often assume co-designed clusters. DIO targets
several unmodified replicas behind one OpenAI-compatible gateway for multi-turn or
agentic clients~\cite{autogen,langgraph}, without engine patches.

\subsection{Affinity mechanism}
On each admitted request with prompt text $p$, DIO computes a stable prefix hash
over the first $256$ characters:
\begin{equation}
h(p) = \mathrm{hash}(p[0{:}256]) \bmod 2^{32}.
\end{equation}
A map $M: h\mapsto w$ records the last worker that successfully served that prefix.
When scoring worker $w$, if $M[h(p)]=w$, a cache affinity bonus
$\mathrm{cacheBonus}_w = C$ (default $C{=}200$\,ms; raised in multi-turn experiments)
is subtracted from $S_w$. Independently, the hybrid term $c_p\mathrm{Hit}_w$ prefers
workers the \emph{engine} reports as currently caching well. After admission, DIO
sets $M[h(p)]\leftarrow w^\star$.

DIO maintains $\mathrm{affinity\_decisions}$ and $\mathrm{affinity\_hits}$ (true when
the chosen worker already owned the prefix). Exposed hit rate
$\mathrm{affinity\_hits}/\mathrm{affinity\_decisions}$ is the primary stickiness
metric for multi-turn evaluation; operators can also compare engine-reported prefix
hit rates under DIO vs.\ RR when live metrics are available. Affinity is
request-level stickiness complementary to RadixAttention~\cite{radixattention}: DIO
increases the chance that the engine's own cache is warm; it does not implement a
second cache. The \texttt{no\_cache} ablation disables the bonus for sensitivity
studies.

\section{Sound admission under unreliable latency prediction}
\label{sec:admission}

\subsection{\texorpdfstring{Why decouple admission from absolute $\hat{y}$}{Why decouple admission from absolute latency}}
Many predictive schedulers implicitly assume $\hat{y}$ is calibrated enough to
compare against an SLO in absolute milliseconds. Section~\ref{sec:mape} shows that
assumption fails for NLMS on dual-T4 (MAPE $\sim$90--130\%). Cold-start priors and
batching can make $S_w$ larger than any reasonable SLO even when true latency is
fine. Gating on $\min_w S_w > \mathrm{SLO}$ then rejects healthy traffic---or, if
priors are optimistic, admits work that will miss the SLO. Predictability-first
serving~\cite{clockwork} and goodput-oriented LLM systems~\cite{distserve,sloawarellm}
motivate treating admission as a policy that must not inherit model bias.

\subsection{Three admission modes}
Ranking is always $\arg\min_w S_w$ among feasible workers. Admission is separate:

\begin{itemize}
\item \texttt{rank\_only}: never reject for SLO based on $S_w$; only hard
VRAM/tier/KV blocks apply. NLMS is used only for ranking.
\item \texttt{empirical} (default): after warm-up ($\ge 8$ samples in a window of
length $64$), reject only if the empirical $p$-th percentile (default $p{=}95$)
exceeds the SLO \emph{and} the best score lies in the worst quartile of feasible
workers. Cold-start does not reject on $\hat{y}$ alone.
\item \texttt{absolute} (diagnostic): reject if $\min_w S_w > \mathrm{SLO}$.
Sensitive to MAPE and cold-start scale; kept to measure disagreement with the
active mode.
\end{itemize}

\begin{algorithm}[ht]
\caption{AdmissionReject$(S_{\min}, m)$}
\label{alg:admission}
\begin{algorithmic}[1]
\Require best score $S_{\min}$, mode $m$, SLO $L$, recent e2e window $\mathcal{Y}$
\If{$m=\texttt{rank\_only}$} \Return false
\EndIf
\If{$m=\texttt{empirical}$}
  \If{$|\mathcal{Y}|<8$} \Return false \Comment{warm-up: do not trust $\hat{y}$}
  \EndIf
  \State $q \leftarrow$ Percentile$(\mathcal{Y},p)$
  \State $Q_{75} \leftarrow$ Percentile of current feasible scores at 75\%
  \State \Return $(q > L) \land (S_{\min} \ge Q_{75})$
\EndIf
\State \Return $(S_{\min} > L)$ \Comment{\texttt{absolute}}
\end{algorithmic}
\end{algorithm}

Counters \texttt{would\_reject\_absolute}, \texttt{would\_admit\_absolute}, and
\texttt{absolute\_vs\_active\_disagree} record, on every pick, whether absolute mode
would have made a different decision; these are the primary metrics for admission
safety (Section~\ref{sec:evalC}). Rejected requests return HTTP 503 with
\texttt{Retry-After}.

\section{Experimental evaluation}
\label{sec:evaluation}

\subsection{Methodology}
\label{sec:method}
\textbf{Hardware and software.} Unless noted, engines are unmodified
vLLM~\cite{vllm} serving Qwen2.5-3B-Instruct~\cite{qwen25} with a Hugging Face
tokenizer behind the \texttt{dio-serve} gateway. Homogeneous dual-T4 and controlled-skew
suites use \texttt{run\_workshop\_final\_suite.py}; multi-turn hybrid, affinity, and
admission suites use \texttt{run\_gpu\_abc\_suite.py}; physical heterogeneous-GPU
cells use \texttt{run\_regime\_d\_hetero.py}. Library multi-seed harnesses
(\texttt{run\_abc\_experiments.py}) complement GPU cells with coefficient and
ablation checks.

\textbf{Experiment families (Regimes~A--D; non-interchangeable).}
We label families for cross-reference. Lettering skips Regime~B: an early single-seed
Locust pilot with longer-decode traces that is not used for any claim in this paper.
\begin{enumerate}
\item \textbf{Regime~A --- matched replicas (real dual-T4):}
  identical peers, $\texttt{max\_tokens}{=}32$, $n{=}10$ seeds $\times$ 30 requests
  (Section~\ref{sec:regimeA}).
\item \textbf{Regime~C --- controlled service-time asymmetry:}
  (i) CPU multi-seed simulation $n{=}10$; (ii) real dual-T4 with one peer under a
  controlled $\times 2$ end-to-end service-time inflation, $n{=}10\times 30$
  (Section~\ref{sec:regimeC}).
\item \textbf{Regime~D --- physical heterogeneity (real T4$+$A30):}
  Tesla~T4 (16\,GB) and NVIDIA~A30 (24\,GB), unmodified vLLM, no injected delay, mixed
  $\texttt{max\_tokens}$, primary cell $n{=}5$ seeds $\times$ 40 requests, plus an
  offset robustness cell and fixed-length slope-sensitivity cells
  (Section~\ref{sec:regimeD}).
\item \textbf{Admission safety (real dual-T4; not lettered as a Regime):}
  $n{=}10\times 40$ with a deliberately tight SLO; a calibration stress test, not a
  throughput comparison (Section~\ref{sec:evalC}).
\end{enumerate}

\textbf{Baselines and metrics.} Round-Robin (RR), Least-Loaded (LL), and
RLS~\cite{haykin2002adaptive} ($d{=}2$, $\lambda{=}0.99$) under the same engines
where applicable. Primary metrics: p50/p99 e2e mean$\pm$std across seeds; MAPE;
routing fraction to each backend; admission reject rate and completions. When the
routing strategy is RR or LL, DIO still runs a \emph{shadow} dual-timescale NLMS
predictor on every completion for diagnostics; the MAPE column is that shadow model,
not evidence that RR routes by $\hat{y}$. Matched multi-node Orca~\cite{orca},
vLLM-distributed, and Production Stack GPU bake-offs are out of scope.

\subsection{Physical GPU heterogeneity: T4 and A30}
\label{sec:regimeD}
Regime~C establishes that DIO ranks correctly when a peer is \emph{made} slow.
The natural objection is that an injected $\times 2$ inflation is a proxy, whereas
real hardware gaps are neither constant nor uniform across the request mix.
Regime~D removes the proxy: two different GPU types, no instrumented delay path,
identical weights, unmodified vLLM on both. M\'{e}lange~\cite{melange} addresses
GPU-heterogeneous \emph{provisioning and placement}; DIO addresses online replica
selection after a heterogeneous fleet has already been deployed, learning from
black-box telemetry alone without requiring an offline latency/throughput
performance-capacity model before deployment.

\textbf{Setup.} One NVIDIA Tesla~T4 (16\,GB GDDR6) and one NVIDIA~A30 (24\,GB HBM2),
each running an unmodified \texttt{vllm.entrypoints.openai.api\_server} with
Qwen2.5-3B-Instruct (fp16), \texttt{--gpu-memory-utilization 0.85}, in a single
datacentre region (E2E Networks On-Demand). Both workers export the Prometheus
\texttt{/metrics} endpoint. The DIO gateway is co-located with the T4 worker and
reaches the A30 over the provider network. Because we do not measure the path-latency
delta, the experiment should not be interpreted as a network-independent speedup;
if anything, co-location may favour the T4. We use the per-token slope $s$ in
$\hat{y}=sN+b$ as a compact measure of the observed service-rate difference between
workers (decode performance for this workload is expected to be strongly influenced
by memory bandwidth, but we do not measure bandwidth directly).

\textbf{Declared VRAM (not a performance profile).} Each backend's VRAM is declared
explicitly (\texttt{--vram} 16000 / 24000\,MB) so the soft/hard VRAM terms of the
joint cost use correct device memory sizes. This is configuration of hardware
memory capacity, not an offline latency or throughput profile of either SKU.

\textbf{Workload design: slope identifiability.} Regimes~A and~C fix
\texttt{max\_tokens}, which leaves the token feature $N$ nearly constant. Under a
near-constant regressor the decomposition of $\hat{y}$ into slope and intercept is
ill-conditioned: many $(s,b)$ pairs fit the data equally well, so the learned $s$
is arbitrary even when $\hat{y}$ itself is accurate. This does not harm ranking ---
a constant absorbed into $b$ cancels when comparing peers --- but it makes any
per-worker slope claim unsupportable. Regime~D therefore mixes
$\texttt{max\_tokens}\in\{32,64,128,256\}$ with varied prompt lengths, giving $N$
genuine spread. Cell~D3 (Table~\ref{tab:d3}) repeats the measurement at fixed
lengths to show how constant $N$ compresses the learned slope gap.

\textbf{Protocol.} Sequential load (one in-flight request), $n{=}5$ seeds $\times$ 40
requests per strategy, fresh gateway process per seed. Strategies: dual-timescale
NLMS, $d{=}2$ RLS, Round-Robin, Least-Loaded. Primary metrics: p50/p95/p99 e2e
mean$\pm$std across seeds, routing fraction to the A30, and paired mean p99
improvement vs.\ RR (wins/$n$). Sequential single-in-flight load isolates ranking
from continuous-batching interactions; concurrent multi-in-flight Regime~D is left
as future work (Section~\ref{sec:limitations}). Direct no-gateway probes on the same
engines give a mean \emph{end-to-end} latency ratio
$\mathrm{T4}/\mathrm{A30}\approx 2.68\times$ on fixed 64-token chats; this is a
workload-level e2e ratio, distinct from the per-token slope ratio reported below.

\textbf{Slope validation.} For every worker we fit an offline least-squares model
to the same $(N,\,\text{observed latency})$ pairs the online learner trained on,
using the gateway's own token feature so both estimators see identical inputs. The
online NLMS slope is then reported against that OLS fit. Because NLMS is a tracking
filter under a normalized step size rather than an unbiased estimator, its slope is
expected to be shrunk toward zero relative to OLS; what matters for the scheduler
is that the ordering and an approximately consistent ratio survive, since
$\mathrm{pick}()$ consumes only relative costs.

\textbf{Online routing results.}
Table~\ref{tab:realD} reports the multi-seed matrix. The headline comparison against
Round-Robin is that both online learners improve mean p99: NLMS by
$\mathbf{33.3\%}$ (SD~$17.4\%$) and RLS by $33.7\%$ (SD~$24.1\%$), each with
$\mathbf{5/5}$ paired wins (exact sign test $p{=}0.031$ under a coin-flip null). A
seed-matched Wilcoxon signed-rank test on per-seed p99 (NLMS vs.\ RLS; $n{=}5$)
yields $W{=}7$ (exact two-sided $p{=}1.00$): \emph{there is no evidence of a median
p99 difference between NLMS and RLS at this sample size}. We therefore do not claim
that dual-timescale NLMS is a more accurate ranker than $d{=}2$ RLS on this cell.
The systems case for NLMS is different: \textbf{comparable central effectiveness to
RLS} under the same linear feature model, with \textbf{$O(1)$ per-update cost}
rather than $O(d^2)$, and \textbf{cleaner, lower-dispersion routing}. NLMS sends a
mean of $\mathbf{89.5\%}$ of traffic to the A30 (SD~$2.1\%$); RLS averages $79.5\%$

NLMS also shows lower seed-to-seed p99 dispersion (SD $1328$ vs.\ $1821$\,ms). RR

\subsection{Hybrid cost on real dual-T4 multi-turn}
\label{sec:evalA}
The next experiments are the primary real-hardware checks of hybrid cost,
affinity, and admission on \emph{homogeneous} dual-T4 (stock vLLM, Qwen2.5-3B, HF
tokenizer, live Prometheus \texttt{/metrics}, \texttt{run\_gpu\_abc\_suite.py},
$n{=}10$ seeds). Workload: multi-turn sessions with long shared system prefixes

\textbf{G1 design: a $2\times2$ confound, and what we can still conclude.}
The two G1 NLMS arms differ in \emph{two} knobs simultaneously:
\begin{description}
\item[\texttt{nlms\_hybrid\_on}] \texttt{engine\_metrics=True}, \texttt{cache\_bonus\_ms=200}
\item[\texttt{nlms\_hybrid\_off}] \texttt{engine\_metrics=False}, \texttt{cache\_bonus\_ms=0}
\end{description}
The published contrast therefore bundles the scraped \texttt{/metrics} fusion
(Contribution~2) with the session-affinity cache bonus (Contribution~1).
We audit this in the text and the appendix rather than silently correcting it
because the audit itself is instructive. The arithmetic is straightforward:
across the 100 snapshots recorded by the campaign, max possible engine-metric
penalty is $1.032$\,ms, against the affinity bonus of $200$\,ms --- a $194{\times}$
ratio.\footnote{Appendix~\ref{app:g1-seeds} and the companion repository
(\texttt{scripts/audit\_g1\_confound.py}) reproduce the decomposition.}

Two additional implementation facts bear on the interpretation. First, \texttt{--enable-prefix-caching} was not passed to vLLM, so the engine never exported
\texttt{vllm:prefix\_cache\_hits/queries} and the $c_p{\cdot}\text{Hit}_w$ term was
identically zero in every run. Second, the ``concurrent'' flag in
\texttt{run\_multiturn\_load} used a synchronous \texttt{httpx.Client}, so at most
one request was ever in flight; $\max(\texttt{num\_running}){=}1$,
$\max(\texttt{num\_waiting}){=}0$, and the $c_q{\cdot}W_w$ term was also zero.

\textbf{What the numbers show.}
Table~\ref{tab:hybrid} and Figure~\ref{fig:evalA} report the measured data unaltered.
Hybrid-on mean p99 is $2000\pm1031$\,ms (median $1633$\,ms) vs.\ hybrid-off
$3378\pm43$\,ms and RR $3388\pm21$\,ms. Per-seed p99 improvement vs.\ RR is
$\mathbf{40.9\%\pm30.5\%}$ (median $\mathbf{51.8\%}$; positive on $\mathbf{8/10}$
seeds). A two-sided Wilcoxon signed-rank test on paired seed p99 (hybrid-on vs.\ RR)
gives $W{=}3$ at $n{=}10$ ($W_+{=}52$, $W_-{=}3$), $p{\approx}0.01$, which is
statistically significant but does not identify \emph{which} knob drove the gain.

Given the $194{\times}$ ratio above, we attribute the effect to the cache-bonus
term (Contribution~1, session affinity), not to the scraped gauge terms
(Contribution~2) --- the reverse of how earlier drafts of this manuscript read the

not the source. Stickiness under hybrid-on is $0.998\pm0.007$ (RR $0.75$).

To correctly attribute the two knobs, we complement the GPU campaign with a
$2{\times}2$ factorial mechanism-study on mock-engines that export the identical
Prometheus gauges but where concurrency and prefix-caching are provably active
($\texttt{peak\_running}{=}4$ on every seed). With $n{=}20$ seeds, the mock
factorial gives $\text{engine\_metrics\_effect} = +2.5\% \pm 28.3\%$ (not
significant) and $\text{affinity\_effect} = +6.9\% \pm 24.9\%$ (not significant at
these low latencies, $\sim$220\,ms). The mock study confirms that the scraped
signal is real but small, and that at the $\sim$3\,s latencies of the dual-T4
regime, the 200--400\,ms cache bonus is the first-order term. The paper keeps the
GPU data as-is under the corrected attribution; a re-run of the factorial on
dual-T4 hardware with \texttt{--enable-prefix-caching} and a multi-threaded load
generator remains on our maintenance roadmap.

\textbf{An unexpected secondary finding.} Hybrid-off sends 81--98\% of traffic to
e0 yet its p99 ($\sim$3378\,ms) is indistinguishable from Round-Robin
($\sim$3388\,ms). The NLMS ranker homogenizes latency across two identical-T4
engines, but strongly favoring one peer at negligible tail penalty is a property
we cannot fully explain from the current data and flag as a question for further
study.

\section{Discussion and limitations}
\label{sec:limitations}

\textbf{What the experiments establish.}
NLMS ranking helps when workers have an observed service gap, either controlled
(Section~\ref{sec:regimeC}) or physical (Section~\ref{sec:regimeD}); it should not
be expected to improve matched replicas (Section~\ref{sec:regimeA}). Prefer
\texttt{empirical} or \texttt{rank\_only} admission when absolute prediction error
is high (Section~\ref{sec:evalC}). Optional affinity and scraped-metric paths are
implementation capabilities and are not sold as independent performance wins here.

\textbf{Limitations.}
\textbf{(i)~Seed count.} The physical primary cell uses five paired seeds
($\times$40 requests) plus an offset five-seed routing-robustness cell on one
T4$+$A30 pair, one model (Qwen2.5-3B), and one cloud region. Small $n$ and
single-model/SKU coverage limit generality; p99 is outlier-sensitive, so we report
mean$\pm$SD, paired win counts, and the offset routing check rather than claiming
broad robustness from five seeds alone. Expanding the primary cell to $n{=}8$--$10$
is the highest-priority follow-up measurement.
\textbf{(ii)~Sequential load.} Regime~D is deliberately one-in-flight, which
isolates ranking from continuous batching but removes the concurrent queue/KV
dynamics that motivate multi-instance serving. Demonstrating that the learned
heterogeneity advantage survives even a small concurrency sweep (e.g., $1/4/8$
in-flight) is the second highest-priority follow-up; without it, claims about
production multi-instance load remain provisional.
\textbf{(iii)~Baselines.} We compare RR, Least-Loaded, and $d{=}2$ RLS under the
same cost shell. We do not evaluate a still simpler EWMA/recent-latency ranker
without a token feature; that baseline is needed to argue that NLMS structure is
necessary rather than merely sufficient among lightweight black-box predictors.
Against RLS we claim comparable central p99 with $O(1)$ updates and cleaner
routing, not superior accuracy.
\textbf{(iv)~Other.} Gateway co-location with the T4 means path latency may favour
the T4; without a measured path delta we do not claim a network-independent
speedup. Direct no-gateway probes and offline OLS are \emph{post-hoc validation},
not inputs to the online controller---DIO does not require an offline
latency/throughput performance-capacity model before deployment. The controlled
dual-T4 study uses an injected delay and is a mechanism validation, not a second
physical heterogeneous deployment. NLMS step sizes and hybrid coefficients are
defaults (Appendix~\ref{app:coeff}), not grid-searched; no $\mu$ sensitivity sweep
is reported. Table~\ref{tab:scope-compare} positions DIO against production routers
without a shared-workload GPU bake-off; the Production Stack static-backend smoke
path establishes installability only.

\section{Conclusion}
\label{sec:conclusion}

DIO is a thin OpenAI-compatible gateway for multi-instance unmodified vLLM
deployments. Matched dual-T4 peers stay near Round-Robin. Under a controlled
service gap and a physical T4$+$A30 pair, dual-timescale NLMS learns a useful
relative ordering from black-box end-to-end telemetry without requiring an offline
latency/throughput model before deployment. On the physical cell it matches $d{=}2$
RLS on central p99 while retaining $O(1)$ updates and more stable routing to the
lower-latency GPU under sequential load. The same model is too poorly calibrated
for a direct absolute SLO gate (MAPE $\sim$90--130\%; $\sim$40\% reject rate under
absolute admission). Keeping ranking and admission as separate policies is a
correctness requirement for predictive gateways built on black-box telemetry.
Source code and artifacts are public.
